# Backend Documentation — Smart Attendance System

## 1. Architecture

```
Flutter App
    |
    | multipart/form-data (image + class_name)
    v
FastAPI  (/recognize-and-mark/)
    |
    |--> AI Module (InsightFace buffalo_l)
    |       detects faces, returns per-face embeddings
    |
    |--> recognition.py
    |       cosine-similarity match against registered embeddings
    |       threshold -> Present / Unknown
    |       dedupe -> one record per student
    |
    v
PostgreSQL
    students | class_sessions | attendance_records
    |
    v
excel_export.py --> .xlsx report (download)
```

## 2. Database Schema

**students**
| Column | Type | Notes |
|---|---|---|
| id | int, PK | |

| department, year, section | string, nullable | |

**class_sessions**
| Column | Type | Notes |
|---|---|---|
| id | int, PK | |
| class_name | string | |
| section | string, nullable | |
| session_date | datetime | defaults to time of creation |

**attendance_records**
| Column | Type | Notes |
|---|---|---|
| id | int, PK | |
| student_id | FK -> students.id | |
| class_session_id | FK -> class_sessions.id | |
| status | enum(present, absent) | |
| similarity_score | float, nullable | null for absent |
| marked_at | datetime | |

Unique constraint on `(student_id, class_session_id)` prevents duplicate attendance rows at the database level.

## 3. API Endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/students/` | Register a student: stores registration number, profile fields, and a face embedding generated from their photo |
| POST | `/recognize-and-mark/` | Core workflow: accepts a classroom image, runs face recognition, matches against registered students, marks Present/Absent, returns a summary |
| GET | `/attendance/history/{class_session_id}` | Returns the attendance record for a past session |
| GET | `/attendance/report/{class_session_id}` | Downloads the session's attendance as an `.xlsx` file |

Full interactive docs (request/response schemas, try-it-out) are auto-generated by FastAPI at `/docs` when the server is running.

## 4. Attendance Generation Logic

1. Classroom image uploaded → validated (file type, non-empty).
2. AI module detects faces and returns embeddings.
3. Each embedding is compared via cosine similarity against all registered students' embeddings.
4. Best match above `SIMILARITY_THRESHOLD` (0.45, tuned during Day 8 testing) → candidate match; below → Unknown.
5. If the same student is matched from multiple detected faces, only the highest-similarity match is kept (deduplication).
6. Every registered student not matched is marked Absent.
7. Results are saved as one `AttendanceRecord` per student per session.

## 5. Known Limitations / Future Work

- Embeddings are stored as JSON text rather than a vector-indexed column; fine for a single class's worth of students, would need `pgvector` or similar to scale to a full college.
- Similarity threshold is a single global constant; could be tuned per-lighting-condition or per-camera in future work.
- Unknown-face count is returned per request but not persisted per session — would need a column on `class_sessions` to show up in history.
